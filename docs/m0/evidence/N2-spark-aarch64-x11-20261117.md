- Host / OS / kernel / desktop: lizhan-spark, Linux aarch64, kernel `6.17.0-1029-nvidia`, X11.
- Versions: Rust `1.100.0`; NSH `0.5.1`; DuckDB `v2.0.0`; duckomo `v0.4.0`, `github-release-unsigned`, `linux_arm64`.
- Input: generated Arrow IPC fixture `/tmp/omo-accept/n2-table.arrow`, verified with PyArrow as 1,000,000 rows × 20 columns (`series_00`…`series_19`), 123 record batches; size 162,640,410 bytes; SHA-256 `26adc15234ea8ef36b44601f8c4b2dfd104ece34149aba8a04bd012c19639d4a`.
- Result: **pass for the spark X11 N2 workload**, using the paging and sorting observations below and a separate main-thread measurement run. The scoped callback-gap metric and its limits are recorded below.

## Measurements

- `fps.log` contains 186 `nsh::fps` samples. The initial load includes a 66.82 ms reported frame-work maximum. This is recorded as a frame-work measurement, not as an input-latency or main-thread-stall measurement.
- The 40 samples retained in `scroll-fps.txt` span pre-scroll, active scrolling, and settling. During active scrolling the displayed cadence was about 11–19 fps. Across the retained scroll samples the `frame` p50 field ranged 1.71–3.80 ms, p95 field ranged up to 9.32 ms, and maximum field ranged up to 10.19 ms. In the later steady samples the p95 field was 5.61–5.76 ms and maximum field was 6.46 ms. The raw telemetry is retained so the startup/settling samples remain visible.
- NSH-reported application RSS peaked at 325.9 MB during the scroll capture. RSS was 298.7–325.9 MB in the retained scroll samples.
- A separate clean-workbench baseline is in [N8 evidence](N8-spark-aarch64-x11-20261117.md): app 200,452 kB and worker 75,784 kB. The N2 value is NSH logger output and no concurrent worker RSS capture exists for the N2 run, so the difference is not a per-process memory attribution.

## Post-fix sort re-fetch

The original million-row UI run exposed that `DataTableColumn::sortable` was left at its NSH default (`false`), so its headers could not emit sort changes. Omobench now enables the property in `crates/omo-app/src/ui/table_view.rs`; the focused `result_columns_enable_sorting` unit test passes.

A bounded UI interaction was then run in an isolated X11 server (`Xvfb :99 -screen 0 1600x1000x24 -ac`, no window manager) with the rebuilt release app and the Linux arm64 worker. The inline query returned three deliberately unordered rows: `(3, c), (1, a), (2, b)`. AT-SPI activated the sort button under the `id` header. The preview request count advanced from 1 to 2, the UI reported `Preview 2 completed with 3 rows.`, and the accessible table cells changed from `3,c,1,a,2,b` to `1,a,2,b,3,c`. This verifies a real ascending header action, worker re-fetch, and displayed order; it is a small interaction fixture, separate from the million-row paging run.

## Main-thread measurement, separate run

A normal release build was run in Xvfb `:104` with the same million-row fixture, `NSH_FPS=1`, and `OMOBENCH_MAIN_THREAD_LOG` set. The Results tab displayed the first rows, and 100 mouse-wheel-down events moved the visible first column from `0` to around `2066`. File → Quit ended the app and flushed the terminal probe record. Screenshots: [first page](n2-main-thread-spark-aarch64-x11-20261117/first-page.png), [after scrolling](n2-main-thread-spark-aarch64-x11-20261117/scrolled.png).

`python3 scripts/summarize-main-thread-probe.py docs/m0/evidence/n2-main-thread-spark-aarch64-x11-20261117/main-thread.jsonl --min-coverage-seconds 20` passed: 1,537 callbacks over 39.649 seconds, GTK `ThreadId(1)`, maximum callback gap **192.268 ms**, maximum overrun relative to the nominal 25 ms interval **167.268 ms**, and maximum sampled ongoing gap 32.662 ms. The terminal record reports `stopped`. The timeout uses GLib default priority 0; callback gaps include main-context work and scheduling delay and can be affected by starvation. They are an observed main-thread service interval, not CPU-only blocking or input-to-render latency. A controlled 250 ms delay was detected in the separate [probe validation](MAIN-THREAD-PROBE-spark-aarch64-x11-20261117.md).

The same run's 37 NSH log lines reported frame p50 fields between 6.01 and 6.58 ms, p95 fields between 7.18 and 39.65 ms, a maximum frame-work field of 176.33 ms, and app RSS up to 290.8 MB. These are rolling statistics, not a single workload-wide percentile. The previous 66.82 ms initial-load frame-work value and earlier scroll telemetry remain distinct measurements above.
